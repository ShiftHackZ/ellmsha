# v2026.10.13 Patch 9 — browser tabs and agent logos

The tab-context-menu placement defect found during acceptance was repaired, rebuilt and verified in the installed app.

## Changes in this candidate

- Use Google for text entered in the browser address bar; explicit URLs retain their normal navigation behavior.
- Adopt native popup contents into the in-app browser's tab strip instead of creating a separate bare macOS window. Keeping the original contents preserves POST bodies, opener communication and script-driven closing.
- Preserve CDP session identifiers in lifecycle replies and errors, so an agent receives completion or failure instead of timing out after a successful tab switch. Wait briefly for the exact native child frame to receive focus before dispatching input.
- Render tab context menus outside the transformed preview panel and clamp them to the viewport, preventing doubled offsets and clipping.
- Place image-based agent logos on a white rounded backing so black artwork remains readable in Dark theme. The logo artwork is not recolored.
- Bump the harness and changed AionUI component to Patch 9, with the 2026-10-13 build date. Other component patch numbers remain unchanged.

## Authentication boundary

The user reports successful Google sign-in through an alternative method in Patch 8, and continued absence of the YubiKey dialog. That is user evidence, not an automated account test.

The installed Electron 37.10.3 implementation does not supply Chrome's generic WebAuthn request UI. Its Chromium client delegate also reports no PIN support. These are distinct limitations: the user's exact request stage was not captured, so a PIN requirement is not established as the cause of this particular attempt. Ordinary popup-tab adoption does not implement a hardware-key chooser, PIN entry or authenticator interaction.

Primary implementation references:

- [Electron 37.10.3 authenticator request delegate](https://github.com/electron/electron/blob/v37.10.3/shell/browser/webauthn/electron_authenticator_request_delegate.h)
- [Chromium 138 authenticator request client delegate](https://github.com/chromium/chromium/blob/138.0.7204.251/content/public/browser/authenticator_request_client_delegate.cc)
- [Later Electron PIN-request cancellation fix](https://releases.electronjs.org/pr/54355)

No real account, security-key operation, authentication cookie transfer or OS permission change is part of the local fixtures. YubiKey authentication remains unverified and unfixed by this candidate.

## Additional WebAuthn candidate

User-supplied [electron-webauthn](https://github.com/iamEvanYT/electron-webauthn) provides a macOS AuthenticationServices bridge and explicitly supports external security-key requests. This offers a potential path without a custom Electron build, correcting the earlier overly broad inference. It is not integrated or hardware-tested. Its [loader](https://github.com/iamEvanYT/electron-webauthn/blob/main/src/index.ts) returns unsupported results on Windows/Linux; its [provisioning guide](https://github.com/iamEvanYT/electron-webauthn/blob/main/docs/entitlements-and-provisioning.md) requires the browser credential capability for arbitrary websites. Main-branch source also needs review of security-key allowCredentials forwarding and private Apple selector use before adoption.
